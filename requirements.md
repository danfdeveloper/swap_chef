# Swap Chef — Requirements

## 1. Project overview
Swap Chef is a web application for publishing, adapting, and sharing recipes while preserving the relationship between original recipes and their forks. Users can inspect automatically generated differences and trace a recipe's ancestry.

## 2. MVP functional requirements

### FR-01 — Accounts and access
- Users can register with a username, email, and password; log in; and log out.
- Passwords are stored as secure hashes, never plaintext.
- The server maintains authenticated sessions.
- Anyone can browse and view recipes without logging in.
- Only authenticated users can publish or fork recipes. Guests attempting to fork are prompted to log in.

### FR-02 — Publish recipes
- Authenticated users can create a recipe with a title, description, preparation time, cooking time, ingredients, and ordered steps.
- Each ingredient has a quantity, unit, and name.
- Publishing records the author and creates version 1.
- The server validates required fields, positive ingredient quantities, nonempty ingredient names, and valid units.

### FR-03 — Browse and view recipes
- The public browse page lists recipes newest first, showing title, author, and fork count.
- Each recipe has a detail page displaying title, description, preparation and cooking times, ingredients, steps, author, version number/history, and a parent link when applicable.
- Recipe data is retrieved from the database through the server.
- MVP browsing is a simple chronological list; search is not required.

### FR-04 — Fork recipes and preserve versions
- Authenticated users can fork a recipe into a new, editable recipe record.
- The fork references the **exact parent version** from which it was copied.
- The original recipe and its saved versions are never modified by forking.
- Saving ingredient or step changes creates a new saved version, preserving earlier versions.
- As specified in the proposal, edits to title or times update the recipe record directly; ingredient or step edits create versions.

### FR-05 — Automatic version comparison
- Users can compare a fork with its parent version.
- The backend computes changes from saved data rather than relying on manually entered change summaries.
- The comparison reports ingredients added, removed, or changed (including quantities/units), and steps added or changed in sequence.
- Ingredient matching uses normalized names where possible, stripping common modifiers.
- Uncertain matches are represented as a removal and an addition rather than an assumed substitution.
- If advanced matching is unreliable, the documented fallback is a simpler report of changed ingredient lines and step text.

### FR-06 — Recipe family tree
- Users can view the chain of parent links from any recipe back to its original recipe.
- Users can view the direct forks of the current recipe.
- Every displayed family-tree node links to its recipe detail page.
- Family-tree data is generated by the server from stored parent-child relationships.

## 3. User interface requirements
- Public browse page.
- Public recipe detail page.
- Login and registration pages.
- Recipe editor for original recipes and forks.
- Read-only version comparison view.
- Read-only family-tree/lineage view.
- Frontend can use mock data while backend endpoints are under development.

## 4. Backend and API requirements
- Node.js and Express handle routing, authentication, sessions, validation, and recipe logic.
- All database access occurs through the server; the browser does not connect directly to SQLite.
- Provide a server route for each required action and a consistent response format.
- Define and agree on the API contract in Milestone 1 before parallel implementation.
- Handle invalid submissions and unauthorized actions without corrupting saved recipe history.

**Suggested endpoint contract (implementation proposal; not prescribed in the source documents):**

| Action | Suggested endpoint |
| --- | --- |
| Register / log in / log out | `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout` |
| List recipes | `GET /api/recipes` |
| Publish recipe | `POST /api/recipes` |
| Get recipe details | `GET /api/recipes/:id` |
| Fork recipe | `POST /api/recipes/:id/forks` |
| Save edits | `PUT /api/recipes/:id` |
| Compare fork with parent | `GET /api/recipes/:id/diff` |
| View lineage | `GET /api/recipes/:id/lineage` |

Confirm endpoint names, request/response schemas, and error formats as a team before coding.

## 5. Data requirements
Use **SQLite** with the following logical records:

- **Users:** username, email, hashed password, creation date.
- **Recipes:** identifier, title, description, preparation time, cooking time, author, creation date, parent-version reference if forked.
- **Recipe versions:** recipe reference, version number, save time.
- **Ingredients:** linked to a recipe version; quantity, unit, name.
- **Steps:** linked to a recipe version; ordered instructions.
- **Fork relationships:** child recipe linked to the specific parent recipe version.

Preserve version history and referential integrity when publishing, forking, and editing. The exact table definitions and constraints are to be agreed during schema design.

## 6. Technology stack
- **Frontend:** React, Vite, CSS.
- **Backend:** Node.js, Express.
- **Database:** SQLite.
- **Development tools mentioned in the proposal:** Cursor Agent and Claude Code (optional assistance; generated code still requires review).
- **Collaboration:** shared GitHub repository, feature branches, reviewed pull requests.

## 7. Quality and acceptance criteria
- Authentication and access restrictions work as described.
- Recipe input validation rejects invalid submissions.
- Publishing persists a complete version 1.
- Forking does not change the parent recipe or its historical versions.
- Multiple saved versions remain retrievable.
- Comparison results are tested against known before-and-after recipe pairs.
- Family-tree navigation correctly handles originals, direct forks, and multi-generation ancestry.
- Frontend and backend use the agreed API contract.
- Every milestone ends with a runnable local application.
- Each contributor reviews another member's code; AI-assisted changes receive the same review and must be explainable by the contributor.

## 8. Optional features — outside MVP
- Search/filter by recipe name, ingredient, or dietary tag.
- Printable PDF export.
- Recipe image upload/display.

Do not treat these as required until the team explicitly expands the MVP scope.

## 9. Open design decisions
These details are **not specified** in the proposal and should be resolved in Milestone 1 or before implementation:
- Exact API paths, request/response payloads, and error conventions.
- Session storage and cookie configuration.
- Supported ingredient units and normalization rules.
- Recipe editor behavior for unsaved forks and repeated edits.
- How version history is selected and displayed.
- Exact comparison output format and step-matching rules.
- Database migrations, testing framework, and deployment/demo environment.
